# Data and audit model

## Canonical entities

For each entity define its owner, stable identity, required fields, schema/version,
source of truth, and allowed references.

All product-owned entities use schema version `1` for the first MVP. Stable identities are generated by the product and remain valid if an external provider changes a title or URL.

| Entity | Owner and stable identity | Required fields | Source of truth | Allowed references |
|---|---|---|---|---|
| `Game` | Product-owned UUID | `schema_version`, canonical title, unique slug, publication state, created/updated UTC timestamps | PostgreSQL | Referenced by `StoreProduct` and public read projections; never identified canonically by a Steam application ID |
| `Store` | Product-owned stable code, initially `steam` | `schema_version`, display name, source state, terms-approval decision reference | PostgreSQL plus the immutable human approval event | Referenced by `StoreProduct` and ingestion configuration |
| `StoreProduct` | Product-owned UUID with unique key `(store_id, external_product_id, region, edition_key)` | `schema_version`, `game_id`, store identifier, external product identifier, region, edition key and label, mapping state, tracking-start UTC timestamp | PostgreSQL and the latest applicable human mapping decision | References exactly one `Game` and one `Store`; referenced by runs and observations |
| `IngestionRun` | Product-owned UUID and unique idempotency key | `schema_version`, `store_product_id`, trigger actor, idempotency key, start/end UTC timestamps, state, adapter revision, failure code if any | PostgreSQL | References one approved `StoreProduct`; may reference one or more `SourceReceipt` records and execution audit events |
| `SourceReceipt` | Product-owned UUID; immutable response identity is SHA-256 of the redacted normalized request identity plus response bytes | `schema_version`, `run_id`, request method and normalized URL without secrets, fetched-at UTC timestamp, HTTP status, response hash, selected source revision metadata, redaction status | PostgreSQL; the external response is evidence for the candidate values but is not canonical state | References one `IngestionRun`; referenced by zero or one accepted `PriceObservation`; full raw body is not retained in the MVP |
| `PriceObservation` | Product-owned UUID plus unique normalized observation identity | `schema_version`, `store_product_id`, `source_receipt_id`, currency, current amount in integer minor units, optional regular amount, optional discount percentage, source-observed timestamp if present, fetched-at timestamp, accepted-at timestamp | PostgreSQL after product validation and acceptance | References one approved `StoreProduct` and one `SourceReceipt`; contributes to current-price and observed-low projections |
| `VerificationDecision` | Product-owned UUID | `schema_version`, human actor identity, subject type and stable identity, decision, reason, immutable input identity, UTC timestamp | Append-only PostgreSQL record | May approve or reject a `Store`, `StoreProduct`, exceptional candidate, dependency, migration, or production checkpoint |
| `AuditEvent` | Product-owned UUID; event ordering uses database commit timestamp plus stable event identity | `schema_version`, actor type and identity, event kind, subject identity, immutable input identity, UTC timestamp, outcome, failure code, related transaction or run identity, redaction status | Append-only PostgreSQL record | May reference any product-owned entity; public output never exposes confidential event fields |
| `PublishedPriceProjection` | Product-owned derived identity equal to `store_product_id` | Latest accepted observation identity, current price fields, observed-low identity and amount, tracking start, publication timestamp | Recomputable from accepted `PriceObservation` records and mapping state | Read by `/api/v1`; never referenced as evidence for an observation or decision |

## State and invariants

- State machine or lifecycle: A `Store` and `StoreProduct` begin as `DRAFT` and become `APPROVED`, `REJECTED`, or `PAUSED` through a human decision. Only an `APPROVED` mapping may create an ingestion run. A run moves `QUEUED` → `RUNNING` → one of `SUCCEEDED`, `FAILED_RETRYABLE`, or `FAILED_FINAL`. A candidate becomes `ACCEPTED`, `REJECTED`, or `DUPLICATE`. Publication is enabled only while the mapping is approved and at least one accepted observation exists. Pausing publication does not delete observations or audit evidence.
- Cross-entity invariants: Every observation refers to an approved store product at acceptance time; every store product refers to exactly one canonical game and edition; currency is `KRW` and region is `KR` for MVP publication; money values are nonnegative integer minor units; regular amount, when present, is not less than current amount; discount percentage, when present, is from 0 through 100 and must agree with the accepted source representation or be omitted; the observed low is computed only from accepted observations at or after tracking start; and every accepted observation has one receipt and one successful execution audit event.
- Concurrency and ordering rules: The database permits at most one active ingestion run for the same store product and logical collection window. Unique constraints enforce run and observation idempotency. Acceptance obtains the required database lock on the store product or current projection before comparing ordering. Source-provided observation time is retained when trustworthy, but canonical ordering falls back to fetched-at UTC time. A late observation may be retained as history if valid, but it cannot replace a newer current price. Equal ordering values are resolved by immutable receipt identity, never by process arrival order alone.
- Validation and rejection behavior: The adapter rejects unknown response shapes, mismatched product identity, unapproved mappings, missing current amount, noninteger or negative amounts, unsupported currency or region, inconsistent regular/current amounts, impossible discount values, and responses that cannot be tied to an immutable receipt. Rejection is explicit and audited; the system never silently coerces currency, infers an edition, substitutes zero, or publishes partial data. Corrected input requires a new run or human decision.

## Side effects and idempotency

If the product has retryable side effects, define the idempotency identity, remote
identity retention, duplicate detection, receipt, and partial-failure recovery. If
not applicable, explain why.

- The only MVP external side effect is a read-only HTTP request. It does not mutate remote state and therefore has no remote rollback.
- Each manually triggered run receives an idempotency key derived from the approved `store_product_id`, adapter revision, and operator-selected logical run identity. A retry of the same failed attempt reuses that key.
- Each source response receives an immutable receipt hash. Secrets, cookies, volatile transport headers, and personal data are excluded before the normalized request identity is stored; the response hash identifies the exact received bytes even though the full body is not retained.
- A normalized observation identity includes the store product, currency, current amount, optional regular amount, optional discount, applicable source observation time, and receipt identity. Database uniqueness and service-level comparison detect duplicate or replayed input.
- If a successful fetch confirms the same normalized price state, the run may update separate noncanonical `last_checked_at` metadata but does not create another accepted price observation.
- Receipt creation and network-failure evidence may occur outside the canonical price transaction. Observation acceptance, current projection update, observed-low update, and the successful execution audit event occur in one transaction. Any failure inside that transaction rolls back all canonical changes.
- A `FAILED_RETRYABLE` run may be retried manually. A validation rejection or `FAILED_FINAL` run requires corrected configuration, a new source revision, or a human decision; automatic infinite retry is forbidden.

## Audit model

Define decisions and executions as distinct events when authority and action must
be separated. Specify actor, immutable input identity, timestamp policy, outcome,
failure code, atomicity, append-only behavior, and redaction.

- **Decision events:** Human approvals and rejections are stored as immutable `VerificationDecision` records. They identify the human actor, subject, exact prior state or source evidence, decision, reason, UTC timestamp, and resulting allowed action. A later decision supersedes operational effect but does not alter the earlier event.
- **Execution events:** Source fetches, validation, duplicate detection, acceptance, publication reads, and failures are recorded as `AuditEvent` records linked to the run, receipt, and affected entity identities. Execution authority derives from an applicable human approval; the worker cannot create that authority itself.
- **Actor:** Actors are the human product owner/operator, the authenticated Django service or worker, the Astro read client, or an anonymous public reader. Public page views are not part of the business audit unless later analytics are separately approved.
- **Immutable input identity:** Human decisions reference the exact subject revision and evidence hash. Executions reference the run idempotency key, adapter revision, source receipt hash, mapping revision, and implementation commit when recorded by acceptance evidence.
- **Timestamp policy:** Canonical timestamps use server-generated UTC values. A source timestamp is stored separately with provenance and never replaces the canonical received, accepted, or committed timestamps.
- **Outcome and failure code:** Every state-changing attempt ends with `SUCCESS`, `REJECTED`, `DUPLICATE`, `FAILED_RETRYABLE`, or `FAILED_FINAL`, plus a stable product-owned failure code and redacted diagnostic message when applicable.
- **Atomicity:** The accepted observation, derived current/low state, and successful execution event share one database transaction. If the event cannot be written, the canonical acceptance is rolled back.
- **Append-only behavior:** Accepted observations, verification decisions, source receipts, and business audit events are append-only. Operational projections and `last_checked_at` metadata may be rebuilt or updated but cannot erase their evidence.
- **Redaction:** Authorization headers, cookies, passwords, API keys, session identifiers, database connection strings, full environment values, and unnecessary source payload fields are never written to audit records or logs. Operator identity may be retained internally but is not returned by the public API.

## Data classification and lifecycle

- Public, internal, confidential, personal, financial, or regulated data: Public data consists of canonical game titles, store and edition labels, accepted KRW prices, tracking start, observation time, observed low, and source attribution. Internal data consists of mappings, source hashes, validation decisions, failure codes, adapter revisions, and operator notes. Confidential data consists of runtime secrets, database credentials, admin authentication material, and any future provider key. The MVP has no public-user personal data, payment data, or user financial data. The product prices are public commercial observations, not a user’s financial records. No regulated-data category has been established; source terms, copyright, database rights, privacy, and consumer-presentation obligations still require review before production.
- Retention and deletion: Accepted observations, mappings, decisions, and their audit evidence are retained for the life of the product unless the human product owner authorizes an export-and-delete or legal removal. Full external response bodies are not retained in the MVP; only normalized accepted fields and minimal receipt evidence are retained. Rejected and failed-run evidence is retained until a human-approved operational retention schedule replaces this policy. Canonical deletion is human-only, audited, and must not silently rewrite the meaning of an observed-low claim.
- Backup and recovery: Local and automated-test databases are disposable and may use synthetic data. Production is blocked until encrypted backups, access control, retention, and a successful restore rehearsal are documented. Exact recovery-point and recovery-time targets are open production decisions. A restore must preserve entity identities, accepted observations, decisions, and audit ordering.
- Migration and backward compatibility: Django migrations are the only schema-change authority. Additive changes are preferred. A destructive or irreversible migration requires a human checkpoint, backup evidence, dry-run results, a data-preservation decision, and an explicit rollback or forward-recovery plan. `/api/v1` remains backward compatible for the first MVP; a breaking public-read change requires a new version or coordinated migration. No legacy or competitor-history migration is authorized.
- Fixture and log redaction policy: Deterministic fixtures contain synthetic or explicitly approved public values and never contain credentials, cookies, personal identifiers, or copied full source responses. Live-response fixtures require human approval and must be minimized and redacted. Logs use stable entity, run, receipt, and failure identifiers; they do not print secrets, full request headers, database URLs, or unnecessary raw payloads. Tests must include a negative assertion that known secret patterns do not appear in logs, API output, generated pages, or committed files.
