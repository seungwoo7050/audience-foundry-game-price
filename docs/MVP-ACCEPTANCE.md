# MVP acceptance and evidence

The MVP is complete only when one real user outcome is closed and every blocking
invariant has evidence. Distinguish unit simulation, local integration, sandbox,
manual acceptance, and production evidence.

## Primary closed-loop scenario

- Preconditions and exact inputs: A clean repository at a recorded commit; the six contract documents; pinned Python 3.12.x, Django 5.2.x, Node 22.x at or above 22.12.0, Astro 7.x, one selected PostgreSQL major, and committed lockfiles; an empty migrated integration database; one authenticated operator; one canonical `Game`; one `Store` with code `steam`; one `StoreProduct` containing an operator-approved numeric Steam application identifier, region `KR`, currency expectation `KRW`, one explicit edition key, and a tracking-start timestamp; one deterministic successful source fixture and required negative fixtures; and a separately human-approved live read-only source request for the same mapped product.
- User actions: The operator signs in to Django Admin, verifies and approves the store and store-product mapping, triggers the fixture ingestion, inspects its accepted or failed result, and later authorizes and triggers the one live viability request. A public visitor opens the generated or rendered Astro game page by its stable slug.
- System actions: Django authenticates the operator, verifies approval, assigns an idempotency identity, fetches or loads the source input, creates minimal receipt evidence, validates product identity, region, currency, amounts, ordering, and duplication, and atomically commits the accepted observation, current-price/observed-low projections, and execution audit. Django returns the exact `/api/v1` read contract. Astro consumes that contract and displays the Korean game title, store and edition, current KRW price, observed-low KRW price, tracking-start scope, source, and latest observation time. A replay returns a duplicate/no-op result without a second observation.
- Durable outcome: PostgreSQL contains one approved mapping, one or more immutable accepted observations as applicable, their receipt and audit identities, and a derivable published-price projection. The public Astro artifact presents the accepted state and explicitly says that the low is measured only since tracking began. The audit history survives rebuilding or replacing the Astro output.
- Evidence and exact identity/revision: **Unit simulation:** test names and deterministic fixture hashes prove normalization, rejection, ordering, observed-low calculation, and duplicate behavior. **Local integration:** repository commit SHA, selected runtime versions, migration identifiers, stable game/store-product/run/receipt/observation IDs, API contract fixture hash, backend test output, Astro check/build output, and a screenshot or saved HTML assertion prove the full fixture loop. **Live evidence:** human approval event ID, redacted normalized request identity, UTC request time, HTTP result, adapter commit SHA, response SHA-256, normalized accepted fields, resulting observation ID, and replay result prove the smallest external interface. **Manual acceptance:** the human confirms the displayed product, edition, KRW amounts, source, timestamps, and observed-low wording. **Sandbox:** Not applicable because no approved provider sandbox has been established. **Production:** Not required and must be reported as not performed.

## Blocking negative scenarios

Define expected failure and proof for each applicable case.

- Unauthorized or unapproved action: An anonymous visitor and Astro client cannot reach a mutation path. An unauthenticated operator request is denied. A worker request for a `DRAFT`, `REJECTED`, or `PAUSED` source mapping fails before external collection or canonical write. Evidence consists of authorization tests, unchanged entity counts, and an audited denial without secret disclosure.
- Invalid or conflicting data: Missing current price, noninteger or negative money, non-`KRW` currency, wrong region, current amount greater than an explicitly accepted regular amount, impossible discount, product-ID mismatch, ambiguous edition, or conflicting unique store-product identity is rejected. The prior published price remains unchanged, no accepted observation is created, and the stable rejection code identifies the rule.
- Duplicate/replay/concurrent request: Replaying the same idempotency key or receipt, or concurrently submitting the same logical run, creates at most one accepted observation and one current-state transition. Other attempts resolve as `DUPLICATE`, wait for the existing run, or fail with a stable conflict result. Database uniqueness evidence and final row counts prove the invariant.
- External timeout or failure: A finite timeout, connection error, non-success HTTP status, invalid JSON, or source-level failure moves the run to `FAILED_RETRYABLE` or `FAILED_FINAL` according to the adapter rule. It does not alter the last accepted observation or generated page. The redacted failure record includes the run and request identities but not credentials or raw sensitive headers.
- Partial write or interrupted transaction: Injected failure after candidate validation but before transaction completion leaves no new accepted observation, projection change, or successful audit event. A failed-run record may remain. A subsequent retry completes once without duplicating data. Evidence includes fault-injection integration tests and database state before and after.
- Secret or sensitive-data exposure: Tests seed recognizable fake secret values in runtime-only inputs and assert that they do not appear in logs, source receipts, API responses, Astro output, fixtures, screenshots, Git-tracked files, or completion evidence. Any match blocks completion and requires credential rotation if a real secret was involved.
- Migration/rollback incompatibility: Initial migrations must apply to an empty database and the complete suite must run after migration. Any irreversible or destructive migration without human approval, backup evidence, and a forward-recovery or rollback decision blocks completion. Because the MVP begins with no legacy data, importing or pretending to preserve undocumented legacy state is also a failure.

## Required gates

- Focused checks per implementation atom: Every model or migration change has constraint and migration tests; every normalization rule has accepted and rejected fixtures; every state transition has authority and invariant tests; every adapter change has success, malformed response, timeout, unsupported currency, mismatch, and replay cases; every API field change has a contract test; and every Astro presentation change has a build check plus an assertion for amount, currency, timestamp, source, and observed-low wording.
- Full local repository gate: From a clean checkout and only the committed manifests/lockfiles, create isolated environments, start the selected PostgreSQL major, apply all migrations to an empty database, run Django system and migration checks, run the full backend suite, run Astro type/content checks, build the public site, execute the deterministic fixture closed loop, verify the required negative scenarios, scan tracked and generated output for secret patterns, and finish with a clean Git worktree. The completion evidence records the exact commands and outputs actually run; passing status may not be inferred.
- Smallest real external-interface spike: After human source approval, make one live read-only request for one mapped Steam application identifier, validate and store one KRW observation, render it through the exact API/Astro path, and replay it to prove idempotency. Capture only redacted request metadata and response hash. Failure to obtain permitted, stable-enough input blocks external acceptance but does not justify substituting competitor data or widening scope.
- Manual human checkpoint: Required before source terms acceptance, login or credential entry, source activation, first mapping approval, live request, dependency with material license obligations, destructive migration, public naming/domain use, production deployment, and any future payment, affiliate, advertisement, analytics, email, or user-consent feature. The human also performs the final page comparison for the mapped game and records approval or rejection.
- Dependency, security, privacy, and license checks: Verify runtime compatibility, exact lockfiles, direct dependency purpose/source/version/license, unresolved security advisories, no competing lockfiles, no copied competitor data/code, no secret in Git or public bundles, admin routes separated from public reads, minimized source receipts, no public-user personal data in MVP, and visible deferral of production backup, retention, monitoring, legal, and privacy decisions.

## Completion report

Require exact local and remote commit SHA, clean state, checks actually run, success
and failure evidence, external state changed, rollback path, blockers, deferred
work, and any claim that could not be proved.

The later completion report must state the local commit SHA and, only if a remote exists, the exact remote SHA and branch; whether the worktree is clean; runtime and dependency versions; migrations applied; every command actually run and its result; stable IDs and hashes for the successful local and live paths; evidence for each blocking negative scenario; whether any external state was changed (expected: read-only request only); the local database and generated-site rollback or rebuild path; unresolved blockers; deferred production work; and every statement that remains an assumption. No `COMPLETION-REPORT.md` is created during this documentation step.
