# Technology decisions

Technology follows the product contract. Record why each choice is the smallest
adequate option for the first closed loop.

## Runtime and repository layout

- Language/runtime and exact supported versions: Backend code targets Python `3.12.13` and Django `5.2.x LTS`, using the latest compatible patch resolved by the approved lockfile. Public-site code targets Astro `7.x` and TypeScript on Node.js `22.22.0`. PostgreSQL major `17` is selected and must remain equal across local integration, CI, and any preview environment; the initial local image is `postgres:17.6-bookworm`. Patch updates within the fixed Django, Astro, and PostgreSQL 17 families require the full repository gate. Authoritative compatibility references: [Django/Python compatibility](https://docs.djangoproject.com/en/5.2/faq/install/), [Django 5.2 support status](https://www.djangoproject.com/download/), [Astro prerequisites](https://docs.astro.build/en/install-and-setup/), and [Django PostgreSQL support](https://docs.djangoproject.com/en/5.2/ref/databases/).
- Package/build tool and lock strategy: Python metadata lives in one `backend/pyproject.toml` and is managed with `uv 0.7.20` using the single committed `backend/uv.lock`. JavaScript metadata lives in one `web/package.json` and is managed with `npm 11.4.2` using the single committed `web/package-lock.json`. No dependency addition may create competing lockfiles. Direct dependencies use an approved compatible version range, while the committed lockfiles and runtime images reproduce exact resolved versions. Tool or dependency updates are accepted only after the full repository gate passes.
- Repository layout: One monorepo with `backend/` for Django, ingestion, administration, persistence, and the read API; `web/` for Astro public pages and public assets; and `docs/` for the six starting-contract documents. The two applications may have independent dependency manifests and checks, but they share one product history and one acceptance gate. Astro never imports Django internals or accesses the database directly.
- Local development environment: Local development requires Python 3.12.13, Node.js 22.22.0, PostgreSQL 17, uv 0.7.20, npm 11.4.2, and Git. Configuration is supplied through untracked environment variables or an untracked local environment file. Container orchestration is not a fixed decision; it may be added only if it reduces reproducibility work without introducing a second unsupported runtime path. Local external-source work defaults to deterministic fixtures until the human source checkpoint is complete.

## Application architecture

- Primary components and responsibilities: Django owns canonical entities, database constraints, operator authentication and Django Admin, human source/mapping decisions, source adapters, manually triggered ingestion, validation, idempotency, audit evidence, current-price and observed-low derivation, and the versioned read-only API. PostgreSQL owns durable canonical and audit state. Astro owns Korean public routing, page rendering, presentation components, and basic title navigation. The external store adapter is isolated behind a product-owned interface so a provider change does not change canonical identities or public semantics.
- Persistence and transaction boundary: Only Django writes PostgreSQL. Observation acceptance, current-price projection, observed-low projection, and successful execution audit are committed in one database transaction. External HTTP reads occur outside that canonical transaction; their minimal receipts are linked into the transaction. Astro and browser code have no database credential and no write path.
- Interface style and schema mechanism: Django exposes a read-only JSON interface under `/api/v1`. The MVP schema is defined by explicit response fields, deterministic contract fixtures, backend response tests, and matching TypeScript types in `web/`. The exact schema-generation library is not selected; adding one is optional and must not delay the first contract test. No public write API, GraphQL endpoint, direct database sharing, or client-authoritative price computation is allowed.
- Background, scheduled, or concurrent work: The first loop uses a Django management command or an authenticated operator action to run one ingestion synchronously or as a single product-controlled process. An external queue, distributed worker, scheduler, and unattended retry are not part of MVP. Database uniqueness, locking, and transactions still protect against duplicate or concurrent manual requests. Scheduled collection may be considered only after the manual loop and source permission are proven.

## Dependencies

- Preferred existing capabilities: Use Django’s ORM, migrations, forms, authentication, permissions, management commands, test framework, and Admin before adding substitutes. Use PostgreSQL constraints and transactions for persistence invariants. Use Astro’s routing, components, build/check commands, and server-side or build-time data fetching before adding a separate frontend framework. Prefer Python and Web standard-library capabilities when they are adequate. A small maintained HTTP client or PostgreSQL driver may be added through the normal review process rather than implemented in-house.
- Dependencies that must be pinned rather than copied/forked: Django, the PostgreSQL driver, Astro, TypeScript, official Astro integrations actually required by the selected rendering/deployment mode, and any HTTP, validation, or testing package are installed through package managers and pinned by lockfiles. Their source trees must not be copied into the repository. A fork requires a separate human decision, maintenance owner, license record, and exit plan.
- Forbidden or unreviewed dependencies: Competitor APIs, datasets, mappings, or historical-price dumps; packages without an identified source, version, license, and maintenance status; dependencies installed directly from an unreviewed branch or mutable URL; duplicate frameworks that replace adequate Django or Astro capabilities; code generators whose generated output cannot be reviewed; and packages that require credentials, telemetry, remote mutation, or restrictive terms not approved by the human product owner.
- License and advisory acceptance process: Before merge, record each direct dependency’s name, exact resolved version, upstream source, license, and purpose. A human reviews any copyleft, network-copyleft, source-available, commercial, data-use, telemetry, or attribution obligation. Security advisories are checked before the initial lock and on updates. A dependency with an unresolved material license or advisory is rejected or isolated until the human accepts the documented consequence. Production use also requires a generated dependency/license inventory.

## Verification technology

- Focused test tools: Backend domain, validation, transaction, idempotency, and API tests use Django’s built-in test framework against the selected PostgreSQL major for integration-sensitive behavior. Pure normalization logic uses deterministic unit fixtures. Frontend verification uses Astro’s type/content check and production build; the MVP does not add a separate browser or frontend unit-test framework unless interactive logic makes it necessary. Contract fixtures are validated on both backend output and Astro consumption.
- Repository gate: From a clean checkout, the gate must install from both lockfiles, run Django system checks, verify that no model change lacks a migration, apply migrations to an empty PostgreSQL database, run the complete backend test suite, run Astro checking, build the public site, execute the local fixture closed loop, and confirm a clean Git worktree. The exact commands are committed only after the two package managers are selected.
- External integration or viability environment: One human-approved live read-only Steam request is run separately from deterministic tests. It records the redacted request identity, UTC time, HTTP result, adapter revision, response SHA-256, normalized output, and replay result. It does not run in the normal test suite, does not require bulk access, and is not evidence of production readiness.
- Secret, license, schema, migration, and compatibility checks: Repository and generated-output scans must find no known secret patterns or local environment files. Dependency and license inventories must match the lockfiles. API contract fixtures must match backend and TypeScript representations. Migration checks must prove an empty-database apply path and expose irreversible operations. The gate must run on Python 3.12.x, Django 5.2.x, Node 22.x, Astro 7.x, and the selected PostgreSQL major; untested runtime upgrades are not accepted silently.

## Environments and deployment

- Local, test, preview, and production boundaries: `local` is developer-controlled and uses fixtures by default. `test` is isolated, disposable, and contains synthetic data only. `preview` may render the Astro site against a nonproduction database containing approved test observations, but it has no production secrets or automated live collection. `production` is not created or required for MVP completion and may not be inferred from a successful local or preview run.
- Configuration and secret injection: Nonsecret defaults may be committed. Database credentials, Django secret material, admin credentials, provider keys, hostnames, and deployment tokens are injected at runtime from an untracked environment or later secret manager. Django and Astro receive only the minimum variables needed for their component. A secret must never be placed in public Astro variables, browser bundles, fixtures, logs, screenshots, or completion evidence.
- Production setup deferred from MVP: Hosting provider, domain and DNS, TLS termination, CDN, production Astro adapter or static-publish target, Django application server, database service, backup destination, restore objectives, monitoring, analytics, scheduler, email, affiliate integration, advertisements, capacity planning, incident response, and production data retention are all deferred. Each requires a later decision and evidence; none may be smuggled into the first closed loop as an assumed capability.
